## 2. 분업

| 담당 | 범위 |
|---|---|
| Cowork | App 층 배치 판단, 데이터·실행 층, 제어 층 뼈대 + IDLE·STICK_INSERT |
| 코덱스 | 나머지 7단계 이식 |

지시서: `설계문서/작업문서/코덱스_지시서_시퀀스_7단계.md`

IDLE과 STICK_INSERT를 Cowork가 맡은 이유:
- IDLE은 Halt 진입·복귀 순서가 대기 전류 71 µA를 좌우한다
- STICK_INSERT는 비동기로 바뀐 9회 측정과 맞물린다
- 두 단계가 같은 파일 안의 본보기가 되어, 나머지 7단계는 반복 작업이 된다

코덱스는 플래시 초과를 확인하고 **지시서대로 멈췄다.** 커밋하지 않았다.

### 2-1. 분업 범위를 줄였다 (2026-11-03 오후)

이후 코덱스 역할을 **깃 작업(커밋·푸시·브랜치)으로 한정했다.**

7단계 이식에서 분업의 이득이 나오지 않았다. 플래시 초과로 중단되어 결국
다시 봐야 했다. 이어진 작업(시간축 전환, LCD 표시 대조)은 기존 FW와 새 코드를
한 줄씩 맞춰 보는 일이라, **지시서를 쓰는 비용이 코드를 쓰는 비용보다 크다.**

잃는 것은 빌드 반복이다. 코덱스는 빌드를 스스로 돌릴 수 있지만, Cowork는
매번 "Rebuild 하고 로그 주세요"를 거쳐야 한다. 이날만 일곱 번 왕복했다.
플래시를 또 깎아야 하는 상황이 오면 그때 다시 꺼낸다.

## 3. 플래시 한도 초과와 감축

### 3-1. 1차 경과 — 7단계 이식 직후

| 시점 | 필요 | 한도 8,064 B 대비 |
|---|---|---|
| 7단계 이식 직후 | 8,638 B | +574 |
| 최적화 전략 Size | 8,318 B | +254 |
| Loop unrolling 끔 | 8,291 B | +227 |
| Multi-file Compilation | 8,203 B | +139 |
| 슬롯 통계 끔 | 8,163 B | +99 |
| USART 벤더 함수 2개 교체 | **8,053 B** | **−139 (통과)** |

상세와 쓰지 않은 카드는 설계서 §9.

### 3-2. 판단 순서를 한 번 틀렸다

처음에 레지스터 직접 접근(어려움)을 먼저 제안했다가, 사용자 질문을 받고
컴파일러 옵션(공짜)을 건너뛴 것을 발견했다. 위험 없는 것부터 쓰는 순서로 고쳤다.

결과적으로 **위험 없는 조치만으로 475 B**를 줄였고, 낮은 위험 조치는 110 B만
썼다. 높은 위험(깨우기 핀)은 손대지 않았다.

### 3-3. RAM도 한 번 막혔다

패턴: **0페이지 포화** — 8비트 주소로 닿는 256 B 영역에 변수가 다 들어가려다 넘침.

데이터 모델이 `small`이라 모든 변수가 0페이지로 가는데, 0x100~0x2FF 512 B가
비어 있었다. 기존 펌웨어는 RAM 변수가 126 B뿐이라 이 문제를 만나지 않았다.

조치: 프로젝트 전용 링커 설정 `EWSTM8/MFx_Layered.icf`를 만들고,
큰 버퍼 5개를 `__near`로 옮겼다. 스택 바로 아래 64 B는 완충으로 비워 두었다.

### 3-4. 2차 — `APP_CTRL_Cmd`를 넣자 669 B 초과

`APP_CTRL_Cmd`를 200~300 B로 봤는데 **680 B**였다. 빗나간 이유는 덤프를
패스마다 4바이트씩 내보내는 상태기계로 만들었기 때문이다. 8개 상태를 들고
다니는 비용이 송신 자체보다 컸다.

| 조치 | 줄인 양 |
|---|---|
| 덤프를 블로킹 송신으로 되돌림 | 176 B |
| **시간축 1 ms → 10 ms, 16비트 전환** | **560 B** |
| UART 벤더 함수 2개 → 레지스터 직접 | 285 B |
| **합계** | **1,021 B** |

결과 **7,663 B / 8,192 B, 여유 529 B.**

### 3-5. 시간축 — .map을 보지 않았으면 못 찾았다

③까지 다 해도 200 B가 모자랐다. 여기서 **남은 .map을 뜯어본 것이 갈림길이었다.**

| 라이브러리 모듈 | 크기 | 정체 |
|---|---|---|
| `long.o` | 385 B | 32비트 더하기·빼기·곱하기·나머지·비교 |
| `long_util.o` | 84 B | 32비트 값 적재·저장 |

소스 어디에도 이 이름이 없다. **컴파일러가 알아서 끼워 넣은 것**이라
.map에만 나타난다. 코드를 아무리 읽어도 안 보이는 469 B였다.

출처는 `HW_Tick_Drive`였다. 가장 긴 대기 300초를 1 ms로 세면 300,000이라
16비트에 안 들어가고, 그 타입이 Optic·Lcd·Measure·Sequence·System_Main
다섯 파일로 퍼져 있었다.

단위를 10 ms로 바꾸니 300초가 30,000이 되어 16비트에 들어갔다.
실제 절감은 예상 400 B를 넘어 **560 B**였다 — 32비트 변수는 계산만 비싼 게
아니라 함수를 부를 때 레지스터를 밀어넣고 빼는 비용도 있었다
(`vreg_util.o` 74 B 감소).

덤으로 두 가지가 풀렸다. TIM4가 1 ms마다 깨던 것이 10 ms마다로 줄었고,
보류해둔 ARR 보정값도 기존 FW의 실측값(분주 128 / ARR 149)을 승계할 수 있게 됐다.

판단 근거와 매크로 설계는 설계서 §7-2.

### 3-6. 교훈

추정이 세 번 다 낮았다.

| 대상 | 예상 | 실제 |
|---|---|---|
| 비차단 전환 후 전체 | 7,200 B | 8,638 B |
| `APP_CTRL_Cmd` | 200~300 B | 680 B |
| 시간축 전환 절감 | 400 B | 560 B |

공통 원인은 **호출 자리에서 생기는 비용을 빼놓고 센 것**이다. 8비트 코어에서는
함수 하나의 본문보다 그것을 부르기 위한 준비가 더 클 수 있다. 다음부터 플래시를
가늠할 때는 .map의 `vreg_util.o`와 라이브러리 모듈을 먼저 본다.

## 4. IAR 프로젝트 정리

QC가 IAR에서 직접 빌드한다는 것을 확인하고 두 가지를 고쳤다.

패턴: **설정된 구성과 빈 구성의 공존** — 한 프로젝트 안에 손질된 구성과
손대지 않은 구성이 같이 있어, 어느 쪽을 고르느냐에 따라 결과가 달라지는 상태.

최적화 설정은 `.ewp` 파일에 저장되므로 QC가 다시 맞출 필요가 없다. 문제는
그 설정이 **Debug 구성에만 들어갔다는 것**이었다.

| 항목 | Debug | Release |
|---|---|---|
| 대상 칩 | STM8L151F3 | 선택 안 됨 |
| 데이터 모델 | small | medium |
| 최적화 전략 | Size | Balanced |
| 스택 크기 | 0x100 | 미지정 |
| hex 생성 | 켜짐 | 꺼짐 |

데이터 모델이 small이 아니면 `.icf`의 RAM 분할 전제가 깨진다. 기존
`MFx_New_Ver`도 같은 상태였고, 지금까지 Debug만 써서 밟지 않았을 뿐이다.

조치:
- **Release 구성 삭제.** 둘을 똑같이 맞추는 대신 하나만 남겼다. 맞춰 두면
  앞으로 설정을 바꿀 때마다 두 군데를 고쳐야 하고, 한 번만 빠뜨려도 같은
  상태로 돌아간다. 구성이 하나면 고를 게 없다.
- **hex 이름을 `MFx_Layered.hex`로.** `OVULATION_MULTI_New.hex`가 그대로
  남아 있었다. QC 책상에 두 펌웨어의 hex가 같이 있으면 구분이 안 된다.

남은 일: QC는 IAR 3.10.4를 쓰고 이 프로젝트는 3.11.4로 만들어졌다.
`MFx_New_Ver_3104`는 **기존 펌웨어**의 변환본이라 무관하다. 출하 전에
`MFx_Layered`의 3.10.4 변환본을 따로 만들어야 한다.

## 6. 실기에서 찾은 결함 2건

둘 다 **빌드로는 안 잡히고 실기에서만 드러나는** 종류였다.

### 6-1. `Q` 명령이 아무것도 초기화하지 않았다

패턴: **지연 쓰기와 즉시 리셋** — RAM에 저장을 예약만 해두고, 그 예약이
EEPROM에 들어가기 전에 리셋을 걸어 예약이 사라지는 것.

어제 결과 저장을 "RAM에 담고 틈날 때 EEPROM으로"로 바꿨는데, `Q`는 그 틈을
주지 않고 바로 리셋을 걸었다. 깨어난 기기는 EEPROM에서 옛 값을 다시 읽었다.

**비차단으로 바꾼 쪽은 잘 됐는데, 그 변화에 맞춰야 할 다른 경로를 빠뜨린 것이다.**

추적 과정에 헛걸음이 두 번 있었다.

1. 레코드가 그대로라서 "`Q`가 안 돈다"고 봤다. 그런데 기존 FW의 `Q`는 EEPROM
   **전체**를 지우는데(`DM_App_Rom_Reset_AllData`), 이식본은 카운터와 에러만
   지운다. **이식 누락을 모른 채 이식본 기준으로 판단한 것**이었다.
2. Insert Count 35라는 숫자만으로는 "`Q`가 안 돌았다"와 "`Q`는 돌았지만 저장이
   유실됐다"를 가릴 수 없었다. QC 프로그램 로그의 `OK` 응답이 갈랐다.

결론: **숫자 하나로 두 가설이 다 설명되면 더 보지 말고 가를 수 있는 관측을
찾는다.** 여기서는 디버거 메모리 창이었다.

조치와 500 ms 상한의 근거는 설계서 §7-5.

### 6-2. 시료 대기에서 물방울이 깜박였다

사용자가 "원본에서는 스틱 꽂으면 깜박임 없이 떠 있었다"고 짚어 찾았다.

패턴: **표시 상태 혼선** — 여러 단계가 같은 아이콘을 쓰는데, 점등과 깜박임의
구분을 잃어버린 것.

기존 FW에서 물방울이 깜박이는 경우는 **반응 대기와 스틱 빠짐 에러뿐**이다.
시료 대기는 켜짐 고정이다.

**외관 문제가 아니라 동작 문제다.** 작업자는 깜박임을 "반응 중이니 기다려라"로
읽는다. 시료를 넣지 않고 기다리다 5분 뒤 시간 초과로 끝난다. 이날 오전부터
완주가 안 되던 것이 이 때문이었을 가능성이 높다.

원인은 에러 표시를 `s_EnterError(코드, 아이콘)` 하나로 합치면서 켜짐·깜박임·
애니메이션 세 종류를 전부 깜박임으로 눌러버린 것이다. 전수 대조한 결과
어긋난 곳이 **6군데**였고, 그중 2건(시료 대기, 과다·과소 시료 확인)을 고쳤다.
남은 3건은 애니메이션 표가 필요해 별건으로 뺐다. 대조표는 설계서 §7-6.
