## 2. QC용 IAR 3.10.4 프로젝트 변환

### 2-1. 배경

QC/생산은 IAR 3.10.4(Embedded Workbench 8.0)를 쓰는데, 개발은 3.11.4(8.3)를 쓴다.
상위 버전이 만든 `.ewp`는 하위 버전이 열지 못한다.

### 2-2. 방법

GUI로 그룹·파일을 일일이 넣는 대신 프로젝트 파일을 직접 편집했다.

1. 3.10.4에서 빈 프로젝트를 새로 만든다 (`MFx_New_Ver_3104\OVULATION_MULTI_New`)
2. 그 파일을 틀로 두고, 기존 3.11.4 프로젝트의 **설정값만** 옮긴다
3. 틀(구조·버전 표기)은 3.10.4 것 그대로이므로 거부되지 않는다

옵션 이름과 `<version>`이 모두 일치하는 것만 옮겼다.

`.ewd`(디버거 설정)는 존재하지 않아 IAR GUI에서 Driver를 ST-Link로 지정해 생성했다.

## 5. 결정 사항

### 5-1. 시스템 tick 10 ms → 1 ms

규격 §10이 "시간 기준은 1 ms tick 하나"로 고정.

배터리 제품이라 인터럽트 빈도 증가가 전류에 미칠 영향을 검토했고, 영향 없다고 판단했다.

| 근거 | 내용 |
|---|---|
| 대기 전류 무관 | `DM_HW_Drv.c:391` — 잠들기 전 TIM4 클럭을 끈다. Halt 중 tick 없음 |
| 활성 구간 영향 미미 | LED 구동 20 mA 대비 ISR 증가분은 수십 µA 수준 |
| 사내 전례 | 규격 §19 — Surearly SMART(STM8L152, CR2032)도 TIM4 1 ms |
| 분해능 | 10 ms는 환산 실수를 숨긴다 (이중 스로틀링 버그: 250 ms 의도 → 실제 6.25초) |

**따라오는 작업**: 기존 시간 상수가 전부 10 ms 단위. 10배 환산 시 `TOTAL_REACTION_TIME` 180,000 등
16비트 범위(65,535)를 넘는다. `uint32`로 확장 필요 → 코드 크기 증가 요인.

### 5-2. TIM4 설정 — 분주 8, ARR 249 (계산값)

기존 설정은 분주 128 / ARR 149였다. 계산값은 155인데 149를 쓰고 있다.
`DM_HW_Drv.c:111~128` 주석에 따르면 **실측으로 보정한 값**이며,
이는 실제 fMASTER가 2 MHz가 아니라 약 1.92 MHz(4% 낮음)임을 뜻한다.

새 설정은 **계산값 그대로** 두기로 했다.

| 항목 | 값 | 근거 |
|---|---|---|
| 분주 | 8 | 1 ms당 250칸. 나중에 실측 보정할 때 세밀도가 분주 16의 2배 |
| ARR | 249 | 2,000,000 ÷ 8 ÷ 1000 − 1 |

기존 보정 비율로 환산하면 239가 되지만 쓰지 않았다.
239는 10 ms 기준 측정에서 산수로 끌어낸 값이고 분주도 다른데,
코드에 박히면 **검증된 값처럼 보인다.** 안 맞춘 값은 안 맞춘 것처럼 보여야 한다.

규격 §11의 `TEMPORARY` 표기를 달고, 보정 전에는 시간 의존 시험을 하지 않는다.
보정 전 모든 시간이 약 4% 길게 나온다 (180초 → 약 187초).

보정 방법은 기존과 동일: 2분 대기(`ERR_RUN_TIME`)를 걸고 실측.

### 5-3. 리턴 타입 `int8_t`

규격 §9·§12 — 8bit MCU, RAM 1 KB. Module 고유 코드는 64~127.

### 5-4. Driver 계층을 주변장치별 6개로 분할

기존 `DM_HW_Drv.c` 한 파일(공개 함수 19개)을 나눈다. 규격 §6 "주변장치 1개 = 파일 1개".

`HW_CLK` / `HW_GPIO` / `HW_ADC` / `HW_UART` / `HW_EEPROM` / `HW_PWR`
(+ 완료된 `HW_Tick`). 파일 목록과 공개 함수는 설계서 §5.

### 5-5. 클럭을 전용 Driver 파일에

`HW_PWR_Drive`에 합치는 안, `System_Main`에 두는 안과 비교해 전용 파일로 정했다.

- 규격 §19에서 Surearly SMART가 클럭을 Driver로 취급한다. 같은 회사·같은 STM8 제품과 맞춘다.
- 파일이 늘어도 플래시는 거의 늘지 않는다. 클럭 설정은 `CLK_SYSCLKDivConfig` 4 B 한 줄이고
  어디에 두든 같은 4 B다. 검토 중 "파일이 늘면 플래시도 는다"고 본 것은 과도한 우려였다.

주변장치별 클럭 on/off는 여기 모으지 않는다. 각 Driver가 `CLK_PeripheralClockConfig()`를
직접 부른다. 모으면 ADC·UART가 모두 `HW_CLK_Drive`에 의존해 Driver끼리 얽힌다.

### 5-6. `SystemSleep_10ms()` 삭제

규격 §7 "대기 루프·지연 함수 금지". 기다림은 "시작 시각 저장 → 다음 `_Process()`에서
경과 확인"으로 바꾼다.

상사 지시("블로킹 구조를 어떻게 하면 좋을지 물어봐")에 대한 답이 이 부분이다.

### 6-1. 문제

### 7-2. 기존 파일 수정 2건

**(1) `Src\stm8l15x_it.c`** — `MFx_New_Ver`에서 복사한 파일

| 위치 | 변경 | 사유 |
|---|---|---|
| 24행 | `#include "main.h"` → `stm8l15x_it.h` + `HW_Tick_Drive.h` | `main.h`를 가져오지 않았고, 규격 §6상 인터럽트 파일이 핀 정의를 알 필요가 없다 |
| 파일 끝 | `INTERRUPT_HANDLER(TIM4_UPD_OVF_TRG_IRQHandler, 25)` 추가. 본문은 `HW_Tick_Isr();` 한 줄 | 규격 §6 "xxx_it.c는 Driver 함수 한 줄만 부른다". 기존은 `User_Main.c:107`에 있었다 |

**(2) `Drivers\STM8L15x_StdPeriph_Driver\inc\stm8l15x.h`** — 벤더 라이브러리 수정

> **라이브러리를 새로 받아 덮어쓰면 이 수정이 사라지고 오류 6건이 재발한다.**
> 백업: `~/stm8l15x.h.bak` (세션 임시. 영구 보관이 필요하면 별도 조치)

원래 221~229행이 고정폭 타입을 직접 정의하고 있었다.

```c
typedef   signed short    int16_t;
typedef unsigned short    uint16_t;
```

`HW_Ret_Code.h`가 규격 §9에 따라 `<stdint.h>`를 포함하는데, IAR의 `<stdint.h>`는
`int16_t`를 `int`로 정의한다. STM8에서 `short`와 `int`는 둘 다 16비트라 **크기는 같지만**
기반 타입이 달라 컴파일러가 재선언으로 막는다 (`Error[Pe256]`, 6건).

조치: 해당 typedef 6줄을 `#include <stdint.h>` 한 줄로 교체. 원본 내용과 사유를
`[MFx_Layered change 2026-11-02]` 주석으로 남겼다.

근거: 규격 §12 "벤더 라이브러리 수정 — 타입 충돌 등 불가피할 때만 + 표시",
§19 부록에서 Surearly SMART가 같은 처리를 했다.

`System_Main.c` 147행 `RST_ClearFlag` 인자에 형 변환을 추가했다 (`Warning[Pe188]` 제거).

### 7-6. 읽히는 것

- 증가분의 58%가 `HW_Tick_IsDue` 하나(125 B)다. 32비트 뺄셈·비교를 8비트 MCU에서
  수행하고 NOT_DUE / DUE / DUE_LATE 세 갈래로 나누기 때문이다. 기존 코드에는 이 함수가
  없었다 — 매번 `while`로 기다렸다.
  대가로 얻는 것: 주기 판정이 한 곳에만 있으므로 이중 스로틀링(250 ms 의도 → 실제 6.25초)이
  구조적으로 불가능해진다.
- 틱 인터럽트가 42 B → 20 B로 줄었다. 기존 핸들러에는 ADC 미추적 틱 보정이 섞여 있었다.
  규격대로 "세기만" 하니 절반이 됐다.

### 7-7. 방침 — 계층마다 재측정

216 B는 뼈대만의 값이다. Module·App을 올리면 계층 간 래퍼와 getter가 추가된다.
**한 계층을 올릴 때마다 측정하고 이 문서에 추가한다.** 넘친 뒤에 알면 되돌릴 것이 전부다.

## 8. Driver 계층 작성 (완료)

규격 §16 순서대로 Driver → (Module) → (App) 중 Driver를 마쳤다.
파일 목록·공개 함수·기존과 달라진 동작은 **설계서 §5**에 있다.

### 8-1. 작성 순서와 결과

| 순서 | 파일 | 비고 |
|---|---|---|
| 1 | `HW_CLK_Drive` | 7 B. `CLK_SYSCLKDivConfig` 한 줄 |
| 2 | `HW_GPIO_Drive` | 논리 ID 8개 + `static const` 매핑 표 |
| 3 | `HW_ADC_Drive` | 채널 3개, Enable → Read → Disable |
| 4 | `HW_UART_Drive` | 링 버퍼 16 B + 폴링 |
| 5 | `HW_EEPROM_Drive` | 범위 검사 추가 |
| 6 | `HW_PWR_Drive` | Halt, 깨우기, WWDG 리셋 |

빌드 2회. 1차에서 경고 1건, 수정 후 **오류 0 · 경고 0**.

### 8-2. 핀 초기화가 오히려 줄었다

| | 크기 |
|---|---|
| 기존 `DM_HW_Drv_GPIO_Init` | 102 B |
| 새 `HW_GPIO_Init` + 매핑 표 | 52 + 32 = **84 B** |

기존은 핀마다 `GPIO_Init(GPIOB, GPIO_Pin_4, ...)`을 한 줄씩 나열했다.
새 방식은 표를 반복문으로 훑는다. 핀이 늘어날수록 차이가 벌어진다 —
기존은 핀당 코드가 붙지만, 표는 핀당 4 B만 붙는다.

규격이 요구한 "논리 ID + 매핑 표"가 코드를 늘린 게 아니라 줄였다.

### 8-3. 수정한 경고 1건 — 휘발성 변수 다중 접근

> 한 문장 안에서 `volatile` 변수를 둘 이상 읽어, 읽는 순서를 컴파일러가 정하게 두는 상태

`HW_UART_Drive.c` 115행, `Warning[Pa082]`.

```c
while ((wCount < wMax) && (s_bRxTail != s_bRxHead))
```

`s_bRxHead`는 인터럽트가, `s_bRxTail`은 메인 루프가 쓴다. 한 문장에서 둘 다 읽는다.

현재 코드로는 실제 오동작이 나지 않는다 — 읽는 중에 바이트가 더 들어와도 다음 호출에
읽힌다. 그러나 "왜 괜찮은지"가 코드에 드러나지 않는다.

조치: 두 색인을 지역 변수에 한 번씩 담고 사본으로 판단한다. 이러면
"이 호출은 들어올 때 있던 만큼만 가져간다"가 코드에 명시된다.

### 8-4. 다음 측정이 진짜다

현재 겉보기 잔여 428 B는 **믿으면 안 된다.** Driver 공개 함수 대부분이 아직
아무에게도 불리지 않아 링커가 뺀 상태다. 상세는 설계서 §9.
