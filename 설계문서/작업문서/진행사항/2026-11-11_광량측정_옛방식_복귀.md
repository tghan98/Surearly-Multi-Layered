## 1. 수석님 참고 자료 검토 (11-11)

자료: `../작업예정/rough_files/done/2026-11-11_슈얼리 멀티 광학 비교 2/` 안의 두 HTML.

- `Optic_Solution.html` (11-11): 포화 원인 설명과 해결안 비교. A안(옛 방식, 목표 원시값 1200) 채택

### 쉬운 설명

- 센서에는 빛을 받으면 차오르는 콘덴서(물통)가 붙어 있다. τ = 100 kΩ × 22 nF = 2.2 ms.
- 지금 FW는 LED를 켜고 20 ms 뒤, 다 찬 뒤에 읽는다. 그런데 물통에 천장(포화)이 있어 빈 스틱과 발색 스틱이 둘 다 천장 근처 → 차이가 눌린다.
- 옛 방식은 차오르는 **도중에** 읽는다. 기기·채널마다 "몇 ms 뒤에 읽으면 1200인지"를 꽂을 때 맞춘다. 천장보다 한참 아래라 빛이 줄어든 만큼 값도 줄어든다.
- 원시값 자체가 지금의 게인 적용값과 같은 1200이 되므로 뒤쪽 판정(556, 시료 비율, 컷오프)은 그대로 쓸 수 있다.

우리 데이터와 맞는 점: 가운데 센서(BT·BC)는 어느 기기든 3600~3750으로 거의 같다(천장에 붙은 모양). 생산 QC에서 25 mIU 양성 4번 중 3번이 NO(`../작업예정/rough_files/2026-11-10_품질 신규FW 확인 결과/HCGM26003/`).

### 코드 대조

| 문서 내용 | 확인 |
|---|---|
| 옛 FW 목표 3000, ADC 샘플링 16 사이클 | 맞음 (`Parameter_define.h` `_nTAGET_LIGHT`, `BSP_HW_Config.c:216`). 수석님 말씀 "사이클 수 16"이 이것 |
| 지금 FW 20 ms 대기, 384 사이클 | 맞음 (`Optic.h:61`, `HW_ADC_Drive.c:34`) |
| 문서의 미확인 "ADC 읽는 동안 LED가 켜져 있나" | **켜져 있다.** `T_Scan`(Apps_MainApplication.c:1328): LED 켬 → 지연 → 가운데 센서 2번(첫 번 버림) → T → LED 끔. T가 곡선에서 조금 늦은 점을 읽는다 |
| 옛 FW 튜닝 대상 | LED마다 1번, T와 C 기준으로 2개만 맞춤(`LED_AutoTunning`:1471). 100·500 count 두 점을 직선으로 이어 3000이 되는 시간을 구함. A안은 4채널 각각 맞춤 |
| 정밀 시간용 타이머 | 지금 코드는 TIM2·TIM3를 안 쓴다 → 쓸 수 있음 |

문서가 쓰인 뒤 바뀐 것(문서 값이 낡음): 플래시 여유 60 B → **107 B**, 판정 T > 1040 / C < 1050 → **T 1080(임신)·1090(배란) / C 1005**, 스틱 빠짐 "광학 6.25 s" → 4단계에서 고침, 2600 게이트 없앰.

### 이식할 때 주의

1. **플래시.** 문서의 튜닝 초기값 식 t = −τ·ln(1 − 1200/S)는 로그 계산이라 못 넣는다. "재 보고 비율로 시간 고치기"를 2~3번 반복하는 정수 계산으로 한다. 21회 정렬 평균과 게인 계산이 빠지는 자리에 들어갈지 map으로 확인한다.
2. **시간 정밀도.** 밝은 기기는 약 0.8 ms에 1200에 닿고, 1 µs 흔들림 = 약 0.1%. 측정하는 몇 ms 동안 인터럽트를 막고 TIM2로 잰다. ADC 샘플링은 16 사이클 수준으로 짧게.
3. **방전 대기.** 매 판독 전 콘덴서를 비워야 한다: LED 끈 뒤 5τ ≈ 11 ms 이상(지금 RECOVER 10 ms). 수석님 말씀 "방전 시간 고려"가 이것.
4. **빠짐 기준 재측정.** 포화가 풀리면 발색 때 C가 지금(최저 728)보다 더 내려갈 수 있다 → `스틱빠짐_스위치+광학.md`의 C 기준은 이식 뒤에 잰다.
5. **덤프.** 게인 칸의 뜻이 충전 시간으로 바뀐다 → PC 쪽(Test_UI) 표시도 고친다.
6. 문서가 권한 사전 실험 중 E1(B안을 따로 만들어 비교)은 금요일 마감 때문에 건너뛴다. 오실로스코프가 있으면 E2(센서 전압 파형)로 포화를 눈으로 확인한다.

## 2. 바꿀 곳과 플래시 견적 (11-11)

### 새 측정 순서

| 단계 | 지금 | 바뀐 뒤 |
|---|---|---|
| 꽂은 직후 초기 측정 (채널 4개) | LED 켜고 20 ms → 21회 변환, 가운데 16개 평균 | LED 켜고 20 ms → **1회 변환** (다 찬 값 S. 범위 1500~3900 판정과 QC 기준값 기록에만 씀) |
| 튜닝 | 계산만: 게인 = 1200 × 100 / S | **실제로 재면서 맞춤.** 채널마다 충전 시간 t를 정해 재고, 1200 ± 25에 들 때까지 고침 |
| 매 측정 (시료 대기, 빠짐 확인, 결과 측정) | 20 ms 대기 → 21회 평균 → × 게인 | 인터럽트 끄고 LED 켬 → t만큼 기다림 → ADC 시작 → LED 끔 → 인터럽트 켬. 콘덴서 비우기 20 ms. **4번 반복 평균** |
| ADC 샘플링 | 384 사이클 (192 µs) | **16 사이클** (8 µs). 옛 FW와 같음 |
| 덤프 "게인" 칸 | 게인 31~80 | 충전 시간 카운트 |

뒤쪽 판정(556, 시료 비율, 컷오프, Intensity 계산)은 손대지 않는다. 측정값이 지금의 게인 적용값과 같은 약 1200 척도라서다.

### 튜닝 방법 — 로그 계산 없이

- 첫 t = τ × 1200 / S. 곡선이 처음엔 직선에 가까워 이 값은 늘 목표보다 조금 짧다.
- 재서 값 f가 1200 ± 25 밖이면 t = t × 1200 / f로 고쳐 다시 잰다.
- 충전 곡선은 위로 볼록해서, 이렇게 고치면 **넘치지 않고 아래에서 다가간다**. 계산해 보면 밝은 기기(S 3900)는 2~3번, 어두운 기기(S 1500)는 5~6번이면 들어온다.
- 10번 안에 안 들어오면 그 채널 OPTIC_FAIL.

### 시간을 재는 방법 — 타이머 대신 소프트웨어 지연

- 인터럽트를 끈 상태의 지연 루프는 매번 같은 시간이 걸린다(옛 FW 방식).
- 실제 µs가 얼마인지는 몰라도 된다. 튜닝이 "몇 카운트에서 1200이 되는지"를 재서 맞추기 때문이다. 중요한 건 반복성뿐이다.
- 그래서 TIM2를 쓰지 않는다. 초기화 코드가 없어 플래시가 준다.
- 인터럽트가 꺼지는 시간은 한 번에 최대 약 5 ms다. 10 ms 틱은 한 번 늦게 처리될 뿐 빠지지 않는다. 화면(LCD)은 메인 루프가 그리므로 영향이 없다.

## 3. 수석님 v1.2로 정해진 것 (11-11 16:17)

자료: `../작업예정/rough_files/done/2026-11-11_Optic_Solution_v1.2.html` 5-6절. 2절의 "수석님께 확인할 것" 중 1·4·5가 여기서 정해졌다.

### 충전 시간 = 인터럽트 끄고 **어셈블리** 지연 루프

- `HW_DelayLoop(n)`: `DECW X` + `JRNE` 두 명령. 1회 3 cycle ≈ 1.5 µs (2 MHz). 별도 `.s` 파일. 약 6~8 B.
- C 반복문이 아니라 어셈블리인 이유: C는 컴파일러 설정에 따라 1회 시간이 바뀔 수 있다. 어셈블리는 명령으로 고정된다.
- TIM2(40~60 B), TIM4(64 µs 단위라 너무 거침)는 쓰지 않는다. CPU와 타이머가 같은 2 MHz로 돌기 때문에, 인터럽트를 막은 루프는 타이머와 정확도가 같다.
- n = 0이면 65,536회(약 98 ms)가 되므로 호출하는 쪽에서 0을 막는다.
- 확인: 프로젝트 코드 모델이 small(`MFx_Layered.ewp` GenCodeModel 0)이라 `RET`와 `.near_func.text` 섹션이 맞다. IAR STM8에서 첫 16비트 인자는 X로 들어오고 X는 함수 안에서 마음대로 써도 된다.

### 한 번 읽는 순서

| # | 동작 | 이유 |
|---|---|---|
| 0 | LED 끈 채로 ≥ 11 ms 대기 (틱, 블로킹 아님) | 콘덴서를 비워 매번 같은 출발점 |
| 1 | ADC 켜기, 채널 선택 | 이 준비 시간이 충전 시간에 섞이지 않게 |
| 2 | 인터럽트 끔 | LED보다 **먼저** 꺼야 켠 직후 끼어들 틈이 없다 |
| 3 | LED 켬 | 충전 시작 |
| 4 | `HW_DelayLoop(n)` | 튜닝된 충전 시간 |
| 5 | ADC 변환 시작 | 하드웨어가 샘플링해 그 순간 전압을 잡는다 |
| 6 | 인터럽트 켬 | 변환을 시작한 뒤에는 끼어들어도 결과가 안 바뀐다 |
| 7 | 변환 끝 기다려 읽기 | 타임아웃이 틱 인터럽트를 쓰므로 인터럽트가 켜진 상태여야 한다 |
| 8 | LED 끔 | |
| 9 | 반복 (예: 5번 재서 가운데 3개 평균) | 매번 0에서 출발 |

인터럽트가 꺼지는 시간은 최대 약 3.5 ms. 지금의 21회 연속 변환(약 4.2 ms)보다 짧다.

2절과 달라진 점:
- 2절은 "변환이 끝날 때까지 인터럽트를 끔"이었다. v1.2처럼 **변환 시작 직후 켜는 것**이 맞다. 그래야 `HW_ADC_Read`의 틱 타임아웃이 살아 있다.
- 평균은 2절의 "4번 평균" 대신 **5번 재서 가장 큰 값·가장 작은 값을 빼고 3개 평균**으로 한다. 옛 FW와 같고, 정렬 없이 "합 − 최대 − 최소"로 계산하면 코드가 작다.
- `HW_ADC_Read`를 채널 선택 / 변환 시작 / 끝 대기로 나눈다(1·5·7단계).
- 덤프의 게인 칸은 루프 횟수가 된다. µs 환산(× 약 1.5)은 PC에서 한다.
